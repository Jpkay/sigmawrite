# Dictation catalog delivery capture

The authenticated catalog loader now journals its returned titles, focus descriptions and other text before returning them. This records material offered on the list even when no dictation is opened. It does not record the unreturned source transcript as visible text. Five focused tests cover authenticated ownership, exact returned payload, capture failure and retry, failed source reads, role refusal and rejected client-supplied ownership.

Audio audit finding: startDictation returns signed storage URLs in server mode, with browserText null. The generic text journal deliberately excludes URLs, so this response does not establish the transcript or bytes of audio offered. Browser fallback text is recorded but is development-only. Reading aloud reuses the already-delivered paragraph, while granular question audio has separate asset assertions. These observations do not establish complete audio coverage or playback. A source-version/checksum binding for dictation audio is still required before any complete-history contract can be enabled.

This change has not been deployed and is absent from the frozen revision 37 candidate. No historical coverage or human approval is created.

Further renderer audit: segment objects currently carry text and audioPath only. renderPendingDictationAudio overwrites stable segment/full paths with upsert and saves provider/model/voice, but no byte digest or exact speech-plan binding. A previously signed path can consequently resolve to regenerated audio. The repair must store immutable content-addressed objects plus a manifest binding each digest to its source text, actual speech input, renderer provenance and segment/full role. Both student and admin full-audio URL selection currently assume key/full.mp3 and must read the manifest together. Existing audio cannot inherit a new transcript certification from a database text match alone; it needs verified regeneration or an explicit incomplete state. A delivery record means audio was offered, not that playback completed or the student mastered its content.

The audio-manifest module now describes source text, ordered speech instructions, speed, renderer provenance, format and SHA-256 of the actual returned bytes. Validation rejects mismatched dictation identity, changed or reordered source, missing segment/full records, altered metadata, mutable paths and changed bytes. Five focused tests and TypeScript passed. This module is not yet connected to rendering, storage or delivery; no production audio or existing coverage record has changed. Storage must enforce immutable writes, and metadata hashes provide integrity checks rather than signatures or proof of correct pronunciation.

The immutable storage adapter now uploads with overwrite disabled, verifies the incoming bytes and content-addressed path before network access, and handles concurrent duplicate uploads by downloading and checking the existing bytes. Authentication, transport and unverifiable-object failures are not treated as success. Eleven manifest/storage tests passed. The renderer is not yet wired to this adapter, so existing stable audio paths remain in use until the migration and reader integration are completed.
